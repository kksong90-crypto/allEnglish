## 최종 목표

## 이번에 재현하고 수정한 문제

1. 서버는 `expectedRevision` 비교를 지원하지만 화면이 이 값을 보내지 않았다. 여러 기기에서 오래된 상태로 저장하면 검사가 생략됐다. 조회 revision(미저장 학생은 빈 문자열)을 요청에 넣고, 저장 응답의 새 revision을 다음 저장에 사용한다.
2. `{ok:false, conflict:true}`도 API 포장상 성공 응답이므로, 화면은 이를 일반 저장 성공처럼 처리할 수 있었다. 충돌은 학생 상태·카운터에 반영하지 않고 최신 서버 상태를 다시 읽는다. 요청과 모순되는 상태 또는 다른 날짜·반·학생의 응답도 확정으로 적용하지 않는다.
3. 예정결석 저장 전 시작된 녹음 조회가 늦게 끝나면 예전 명단을 적용하고 `needsRead`를 지웠다. 조회 세대 번호로 이전 응답을 폐기하고, 진행 중 저장·조회가 끝난 뒤 강제 최신 조회를 수행한다. 로그인 교체·만료에서도 이전 세대 응답을 폐기한다.

## 검증과 제한

- 수정 전 재현 테스트 6건 실패를 확인했다. 수정 후 추가 사례를 포함한 `node --test tests/recording-*.test.mjs` 57건 통과, 세션 재로그인 런타임 검사 및 구문 검사 통과.
- 검증은 합성 데이터 기반 로직 테스트다. 실제 휴대전화·서로 다른 기기·브라우저 종료 후 미전송 입력 복구를 확인한 것으로 확대하지 않는다.
- 통신 결과가 불명확하거나 충돌하면 미전송 대기 건을 자동 재전송하지 않고 서버 재확인을 우선하는 기존 정책을 유지한다. 브라우저 강제 종료 전 미전송 큐의 영구 복원은 아직 제공하지 않는다. 이 항목은 별도 설계·검증 전 실사용 준비 완료로 집계하지 않는다.
- 화면 후보 v8.2.15. 서버는 격리 STAGING v17의 revision 응답을 사용한다. PRODUCTION은 변경하지 않는다.
