# 잠금 직전 저장 전송 보완 · UI8.2.26 (2026-11-14)

목표는 체크하고 화면을 껐을 때 웹앱 전송 대기로 남는 구간을 줄이는 것이다. 화면 잠금/OS 강제 종료 후 모든 저장이 반드시 완료된다는 보장은 하지 않는다.3~5초의 서버 처리 시간을 이번 프런트 수정만으로 없앴다고 주장하지 않는다.

## 변경

- visibilitychange의 hidden 및 pagehide에서 이미 보관된 묶음 큐를 즉시 flush한다. 기존120ms 묶음 타이머가 정지하는 틈을 줄인다. 진행 중인 배치는 병렬로 중복 전송하지 않으며 세션/날짜/검증 전제는 그대로 재확인한다.
- 녹음 단건/묶음 요청에 한해 UTF-8 본문과 앱 내 동시 요청 총량이48KiB 이하일 때 fetch keepalive를 사용한다. 큰 본문·예산 초과·TextEncoder 미지원·조회/다른 쓰기는 기존 경로를 유지한다. 성공/실패/중단 시 예산을 반환한다. 브라우저의 전체64KiB 제한이나 기기 네트워크 중단까지 보장하지 않는다.
- 설정의 최근 저장 처리 시간에 브라우저 요청 대기와 서버 응답 내 단계 시간을 표시한다. 화면이 정지한 시간이 대기에 포함될 수 있음을 밝힌다. 학생 이름/ID/토큰/본문을 진단에 출력하지 않는다.

## 보호와 검사

기기 보관, 학생별 revision/CAS,30명 상한, 순차 배치, 최신 값 재조회, 명시적 보관 검토를 유지한다. 화면이 이미 멈췄거나 이전 배치가 진행 중인 경우 아직 보내지 못한 큐는 재개 후 복구 대상이다.

신규6검사: 타이머 없이 잠금 flush·중복 flush 방지, 진행 중 배치 직렬화, 세션/명단 검증 차단, 잠금/복귀 이벤트 연결, 녹음 전송만 keepalive, 다국어 UTF-8/동시 예산·반환. 화면144/144 통과. 실제 휴대전화 OS 잠금 결과는 별도 확인해야 한다.

공식 근거: https://developer.chrome.com/docs/web-platform/page-lifecycle-api 및 https://fetch.spec.whatwg.org/ . 숨김 전환은 모바일에서 마지막으로 관찰 가능한 시점일 수 있으며, keepalive는 페이지 수명과 분리된 요청 전송을 돕는 옵션이다. 무조건적인 백그라운드 실행 보장이 아니다.

## 공개39 실제 관찰

21:45 KST 격리39 배포(되돌림38), 서버 Code SHA와 API 연결 bootstrap 불변을 편집기 재로드로 확인했다. 초기 한 번 이전 화면이 보였으나 새로고침 후8.2.26을 확인했다. 합성2명 검증에서 전송 유지 요청 사용 표시와 실제 저장을 확인했다.

첫 정상 저장은 브라우저10631ms/서버6648ms였다. 서버 단계: 잠금196·대상2498·기존 체크1574·기록532·공지1546·감사210·캐시90ms. 이는 단일 표본이며 속도 개선의 전후 비교가 아니다.

후속2회는 각각9673/8129ms,16576/13992ms였다. 기존 버전의 다른 검증 탭2개가 남아 있었고 두 요청은 다른 상태 감지→안전 재조회 경로로 끝났다. 잠금 대기는5270/5751ms, 체크 기록/공지 단계는 미제공이었다. 따라서 이를 정상 저장 표본이나 새 keepalive로 인한 지연으로 해석하지 않는다. 이전 탭의 자동 복구가 경쟁했을 가능성은 있으나 원인은 미확정이다. 이전 탭은 정리하고 단일 화면으로 재측정했다.

단일 검증 화면의 후속 정상 해제 저장은 브라우저7557ms/서버5547ms였다. 잠금123·대상2715·체크조회1072·기록402·공지1043·감사130·캐시60ms. 실제 체크 변경과 keepalive 사용을 확인했다. 서버 단계의 합계는 응답에 포함된 측정이며 브라우저 대기 전체와 같지 않다. 기존 검증 화면 정리는 전후 속도 개선 실험이 아니며, 원인이 확정되지 않은 충돌 표본은 정상 쓰기 표본에 합치지 않는다.

## 이어서 줄여야 할 서버 비용

1. 대상 판정과 최신 체크 확인이 주요 비용이다. 개인 범위/결석/휴원/마감 및 저장 직전 CAS를 생략하거나 캐시값으로 대체하지 않는다. 최신성·행 동일성을 보존하면서 원격 조회 횟수를 줄일 후보를 별도 격리 비교한다.
2. 공지 반영은 이번 표본에서 약1초였다. 저장 확인을 빨리 보이게 하려고 공지/감사를 끝났다고 거짓 응답하거나 트리거로 무조건 미루지 않는다. 기존 운영센터·학생웹 동기화 요구를 함께 확인한다.
3. 같은 기기의 여러 창에서 한 보관 항목을 동시 복구할 가능성을 추가 검증한다. 기존 두 경쟁 요청이 이 원인이었다고 확정하지 않는다. 서버 최신 값 보호는 작동했다.
4. 브라우저 잠금 시 실행 보장과 응답 시간 개선은 별도 문제다. 이번 전송 보완이 실제 휴대전화에서 화면 끄기 후 완료를 보장한다고 판정하지 않는다.

최종 복원 정상 저장은 브라우저6190ms/서버4490ms였다. 잠금112·대상1142·체크조회780·기록372·공지1862·감사160·캐시60ms. 최종2/2·저장 준비, 기기 보관 항목 없음. 정상 저장3회도6.2~10.6초였으므로 빨라졌다고 판정하지 않는다. 두 충돌 요청은 표본에서 별도 표시했다.
